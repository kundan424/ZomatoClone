Zomato Clone Backend Engine

A highly scalable, secure, and event-driven food delivery API.

Project Overview

This is the core engine of a food delivery platform. I built it to handle the entire journey of an order—from a user securely logging in and browsing menus, to locking down inventory, processing real payments, and updating the kitchen. My main goal was to build something that wouldn't crash or double-charge people during a busy Friday night dinner rush.

How the Complete System Works (Step-by-Step)

Click through the steps below to follow the exact journey of a single food order traveling through the backend architecture.

When the React frontend sends an HTTP request, it doesn't just walk right in. It hits my Spring Security Filter Chain first. If the user is trying to place an order, the system extracts their JSON Web Token (JWT), validates the cryptographic signature, and sets up a secure context. If the token is missing or expired, the request is instantly rejected with a 403 Forbidden status.

Once cleared by security, the request arrives at the Controller layer. Because I use an API-First design, the request is validated against strict Java Interfaces. This ensures the incoming JSON payload perfectly matches the OpenAPI documentation. If the data is malformed, my Global Exception Handler intercepts it and returns a clean error message before any business logic even runs.

Next, the request enters the Service layer. If the user is simply browsing the restaurant menu, the application bypasses the database entirely and serves the data directly from the Redis Cache for lightning-fast read speeds. If the user is modifying data, the service layer orchestrates the complex business rules.

If the user clicks "Checkout," things get serious. The Service layer immediately talks to Redis to establish a Distributed Lock on the specific food items. Once the inventory is secured, the system safely deducts the stock and saves a brand-new order into the PostgreSQL database with a strict "PENDING" status.

With the database primed, the backend reaches out to Stripe's servers to generate a highly secure Checkout Session. I inject the internal Order ID into Stripe's hidden metadata. The backend then returns the generated Stripe URL to the frontend, and the user is redirected away from the app to complete their payment securely.

The moment the user's credit card is approved, Stripe fires an asynchronous HTTP request (a webhook) to my server's hidden backdoor endpoint. My Webhook Controller catches this event, verifies Stripe's cryptographic signature to prevent fraud, extracts the hidden Order ID from the metadata, and finally updates the PostgreSQL database to mark the order as "SUCCESS". The kitchen is officially notified!

Engineering Challenges I Solved

Click on a challenge to see how I fixed it.

The Problem: Imagine two people trying to order the last slice of pizza at the exact same millisecond. If we only rely on the database, both orders might go through!

The Fix: I implemented a Redis Distributed Lock using the setIfAbsent command. It instantly locks the menu item to the first user, deducts the inventory, and then unlocks it. No more ghost pizzas.

The Problem: My frontend was processing payments, but the database order stayed stuck in "Pending". Stripe was sending the webhook, but Spring Boot was silently dropping it because of a hidden API version mismatch.

The Fix: I wrote a robust fallback method using Stripe's "unsafe extraction" mechanism. Now, even if versions mismatch, the system forces the data extraction and updates the database correctly.

The Problem: I added Spring Cache to make loading order histories blazing fast. It worked too well—when a user placed a new order, they couldn't see it because the system kept serving the old cached data!

The Fix: I redesigned the cache layer. I kept @Cacheable for reading data, but injected targeted @CacheEvict annotations on the checkout methods to instantly wipe the old memory the second a new order is placed.

The Problem: Writing manual getters and setters to convert my massive Database Entities into clean Frontend JSON objects was tedious, messy, and prone to typos.

The Fix: I integrated MapStruct. It automatically generates the mapping code at compile time. This kept my service layer incredibly clean and strictly separated my database layer from the outside world.

Core Technical Learnings

Click to explore my key takeaways.

I learned that modern APIs don't use simple passwords for every request. I configured a stateless JWT (JSON Web Token) system. I learned how to tweak the SecurityFilterChain to safely let webhooks and documentation through the "front door" for free, while strictly demanding valid tokens for checkout routes.

Nobody likes seeing a massive, scary Java stack trace on a webpage. I mastered @RestControllerAdvice to catch crashes globally. Now, if someone tries to order an item that doesn't exist, the system catches it and sends the frontend a polite, clean JSON error message instead of crashing.

I realized that controllers get messy fast when you mix routing, documentation, and logic. I extracted all my Swagger annotations and HTTP routes into pure Java Interfaces. This forces me to design the "contract" first, making my actual controllers beautifully simple.

To test Stripe webhooks, Stripe's servers needed to talk directly to my local laptop. I learned how to spin up the Stripe CLI inside a Docker container to punch a secure tunnel through to my localhost, giving me hands-on experience with modern DevOps workflows.
